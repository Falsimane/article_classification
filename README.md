# CTI Knowledge Graph

> Version française : [README.fr.md](README.fr.md)

Turns raw **Cyber Threat Intelligence** articles (vendor reports, research blogs) into a **STIX 2.1 knowledge graph** stored
in **Neo4j**, and serves it through a web dashboard.

Design rule: **the code verifies, the LLM decides meaning, `stix2` validates.** A local LLM (Qwen family) answers in short
lines under a JSON schema: entities, ATT&CK techniques, relations between numbered items, evidence as sentence numbers.
Everything it proposes is built by `stix2` in strict mode and checked against MITRE ATT&CK v20.0 and the article text before it
enters the graph. IOC values (IPs, domains, hashes) are never generated by the model: rules read them.

```text
 scraped articles           cleaning + triage                 STIX extraction                    storage + visualization
┌──────────────────┐   ┌─────────────────────────────┐   ┌──────────────────────────────┐   ┌────────────────────────────┐
│ SQLite `knowledge`│   │ cti_core (Rust): web noise, │   │ numbered sentences           │   │ Neo4j (:Stix:<Type>)       │
│ + raw HTML page   │──▶│ per-source learned template,│──▶│ entities, ATT&CK techniques, │──▶│ STIX bundle per article    │
│                   │   │ IOC refang                  │   │ relations (proof = sentence #)│   │ React dashboard (reports,  │
│                   │   │ LLM: tactical / operational │   │ IOCs, YARA/Sigma rules       │   │ actors, global graph, Q&A) │
│                   │   │ / strategic / out_of_scope  │   │ stix2 + ATT&CK verification  │   │                            │
└──────────────────┘   └─────────────────────────────┘   └──────────────────────────────┘   └────────────────────────────┘
                          uv run cti-classifier              uv run cti-extract                  scripts/dashboard.sh
```

The repo also holds a **hand-annotated gold set** (`Annotations/`) and a scorer (`cti-eval`) measuring recall, precision and
hallucinations of the extraction.

## 2. Setup from scratch

Three parts: **(A)** the workstation running this repo, **(B)** Neo4j, **(C)** LLM servers, usually on a **remote GPU machine**
reached through SSH tunnels.

```text
 workstation (this repo)                         GPU server
┌──────────────────────────────┐  SSH tunnel  ┌───────────────────────────────────────┐
│ cti-classifier ────────────────── :11434 ──▶│ Ollama  qwen3.8:27b   (classification) │
│ cti-extract / cti-eval / dashboard ─ :8010 ─▶│ vLLM    cti-qwen      (extraction)     │
│ Neo4j (Docker) :7687, dashboard :8095        └───────────────────────────────────────┘
└──────────────────────────────┘
```

Requirements: workstation with Python 3.12, Rust (stable), Node.js ≥ 20, Docker; GPU server with an NVIDIA GPU of **≥ 40 GB**
VRAM (A100 40 GB validated).

### 2.1 Workstation

```bash
sudo apt install -y build-essential pkg-config libssl-dev git curl      # Debian/Ubuntu example
curl -LsSf https://astral.sh/uv/install.sh | sh                          # uv
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh           # Rust (builds cti_core)
# Node.js >= 20 via nvm/fnm/your package manager

git clone https://github.com/Falsimane/article_classification.git && cd article_classification
uv sync                                                                  # Python deps + compiles cti_core (editable)
uv run python -c "import cti_core; print(cti_core.CtiEngine())"          # sanity check
cd frontend && npm install && npm run build && cd ..                     # also done by scripts/dashboard.sh
```

After editing Rust: `cd backend/preprocessing/cleaning/cti_core && cargo test && maturin develop --release`.

### 2.2 Neo4j

```bash
docker compose up -d neo4j        # Browser http://localhost:7474, Bolt bolt://localhost:7687, neo4j / password123
```

Change the password with `NEO4J_AUTH=neo4j/<pwd>` **before** the first `up`, and `NEO4J_PASSWORD=<pwd>` for the Python side.

### 2.3 GPU server: vLLM (extraction)

Model: **`ukisai/Swift-1.5-Qwen3.8-27b-W4A16-AWQ`**, a Qwen3.8-27B derivative with bounded reasoning, INT4 (W4A16 AWQ). It fits
one A100 40 GB with a ~238k-token KV cache (≈ 7 concurrent 32k-token requests) and is served as `cti-qwen`. Reference scores
were measured with it. Alternative: `Qwen/Qwen3.8-27B-FP8` (only ~49k tokens of KV cache on 40 GB: ~2 concurrent requests).

```bash
# On the GPU server
python3 -m venv ~/vllm-env && source ~/vllm-env/bin/activate
pip install --upgrade pip && pip install vllm        # validated: 0.32.0
nvidia-smi                                            # pick a FREE GPU

CUDA_VISIBLE_DEVICES=1 vllm serve ukisai/Swift-1.5-Qwen3.8-27b-W4A16-AWQ \
  --served-model-name cti-qwen --host 127.0.0.1 --port 8010 \
  --language-model-only --max-model-len 32768 \
  --gpu-memory-utilization 0.92 --max-num-seqs 8 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_coder
```

| Option | Why |
| :--- | :--- |
| `CUDA_VISIBLE_DEVICES` | always set it: vLLM otherwise grabs GPU 0, maybe busy, and engine init fails. Never use someone else's GPU without consent |
| `--served-model-name cti-qwen`, `--port 8010` | client defaults (`CTI_OPENAI_MODEL`, `CTI_OPENAI_URL`) |
| `--host 127.0.0.1` | reachable only through the SSH tunnel |
| `--language-model-only` | skips the vision tower (saves VRAM) |
| `--max-model-len 32768` | **the whole article is sent in one call**; longer ones are refused and marked failed with the reason |
| `--max-num-seqs 8` | concurrent requests; client `CTI_LLM_SLOTS` must be **≤** this value |
| `--reasoning-parser qwen3` | separates reasoning from the answer (reasoning is off by default client-side) |
| `--enable-auto-tool-choice --tool-call-parser qwen3_coder` | **mandatory** for tool-call turns |

Prefix caching is on by default: every call on an article starts with the same text, which the server re-reads from cache
instead of recomputing. First start takes ~4 min (weights download, `torch.compile`, flashinfer JIT); if flashinfer JIT
fails, `export VLLM_USE_FLASHINFER_SAMPLER=0`. Run inside `tmux`/systemd. **Sanity check before any benchmark** (a badly
loaded model answers without errors but does not read the text):

```bash
curl -s http://127.0.0.1:8010/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"cti-qwen","messages":[{"role":"user","content":"What is 17 x 23? Number only."}],"max_tokens":16,"temperature":0}'
# expected: 391
```

### 2.4 GPU server: Ollama (classification)

```bash
ollama pull qwen3.8:27b
OLLAMA_CONTEXT_LENGTH=12288 OLLAMA_HOST=127.0.0.1:11434 ollama serve
```

One `num_ctx` only: two different values force Ollama to reload the model. The server's `OLLAMA_CONTEXT_LENGTH` must equal the
client's `OLLAMA_NUM_CTX` (12288); a context overflow truncates the *start* of the prompt, i.e. the system prompt. vLLM (92 %
of VRAM) and Ollama do not fit together on one 40 GB GPU: use separate GPUs, or classify first, stop Ollama, then start vLLM.

### 2.5 Tunnels and environment

Never run `ollama`, `vllm` or `systemctl` from the workstation: they are server-side commands.

```bash
ssh -N -L 8010:127.0.0.1:8010   <user>@<gpu-server>      # vLLM
ssh -N -L 11434:127.0.0.1:11434 <user>@<gpu-server>      # Ollama
curl -s http://127.0.0.1:8010/v1/models | head -c 300    # must list cti-qwen

cp .env.example .env && set -a && source .env && set +a  # no automatic .env loading
```

Set `CTI_LLM_SLOTS=8` to match `--max-num-seqs 8` (code default is 10). **Never more simultaneous requests than slots**: behind
an SSH tunnel an abandoned request keeps occupying the server; `llm.py` waits for a free slot before sending. The same applies
to `--workers`.

### 2.6 Input data

Under `backend/data/` (git-ignored; relocatable with `CTI_DATA_DIR`):

```text
sources/cti_knowledge.db                       SQLite, table `knowledge` (id, site_name, url, title, publication_date, content)
raw/html_pages/<site>/<sha1(url)[:16]>.html    the raw HTML page of each article
```

Cleaning reads **the HTML page, never `content`** (a Markdown export has already lost links, code blocks and hidden elements).
The scraper producing these is not in this repo.

### 2.7 Check

```bash

uv run python backend/preprocessing/classifying/evaluate_cleaning.py

```

## 3. Cleaning architecture

**Goal:** turn a raw HTML page (menus, banners, social buttons, cookie notices, footers) into **canonical Markdown** containing
only the article, with code blocks, tables and IOCs intact and in place; then classify it.

```text
HTML page ─▶ cti_core.process_html ─▶ canonical Markdown + sections ─▶ split_blocks ─▶ budgeted context ─▶ LLM (Ollama)
 (disk)       (Rust, structural)                                       (atomic blocks)                          │
    ▲                 │                                                                                         ▼
    │        learned per-source template                                            article_classifications (SQLite):
    └─────── site_boilerplate ◀── learn_site_boilerplate (whole corpus)               clean_markdown, category, scores
```

Principles: **universal** (no publisher/actor/tool list anywhere in Rust; noise is detected by DOM structure, then by learning
each source's template from the corpus); **atomic** (a code block, table or paragraph is never moved or cut); **faithful** (no
entity or IOC extraction here: IOCs stay in the narrative); **deterministic** (Rust, no model: same HTML, same text).

### 3.1 The Rust engine `cti_core`

PyO3 extension (built by `uv sync`) exposing `CtiEngine`; `html.rs` handles the DOM, `lib.rs` Markdown/sections/chunking.
Exposed types: `PreprocessingResult` (`is_processable`, `reject_reason`, `clean_markdown`, `sections`), `ArticleSection`
(title, level, content, `heading_path` "H1 > H2 > H3", atomic `blocks`, `is_appendix_ioc`), `MdBlock`, `Chunk`.

1. **Fast reject** (`check_viability`): empty pages, shells and **scraping error pages** (short document containing "access
   denied", "403 forbidden", "just a moment", "enable javascript", captcha…) get a `reject_reason` and cost no LLM call.
2. **HTML → blocks** (`html.rs`). The DOM carries what a Markdown export lost: what is a link and where it points, what is
   code, a table, a heading, a hidden element. Noise removal is structural:

   | Mechanism | Effect |
   | :--- | :--- |
   | Never-read elements | `script`, `style`, forms, navigation, media |
   | Hidden elements | `hidden` attribute, `display:none`… |
   | React streaming boundaries | `<template id="B:n">` replaced by the content of `<div hidden id="S:n">` |
   | Navigation | block made of internal links with no prose; heading that is a link to another page of the site |
   | Content root | descend to the child carrying ≥ 85 % of the non-link text, as long as what is left aside carries nothing technical (code, table, IOC); a sibling with ≥ 12 words of prose stops the descent |
   | Unescaped writing placeholders | `cmd /c <command>`, `.[<victim_id>]`: an unknown tag without a dash is rendered **as written**, not dropped |
   | IOC anchors | a link anchor of ≤ 4 words that carries an IOC *is* the indicator |
   | Page-builder shortcodes | `[name key="…"]…[/name]` left in the HTML are removed |

3. **Common passes** (`finish`): duplicates, header metadata, head/tail trimming, orphan headings; then rendering (`#` headings,
   paragraphs, `- ` lists, fenced code, `|` tables) and splitting into **sections**.
4. **Refang** (`refang`, outside code blocks): `hxxp` → `http`, `example[.]com`, `example(dot)com`, `user[at]example.com`,
   half-closed forms `domain.]com` / `domain[.com`.

### 3.2 Learned per-source template (`cleaner.py`)

A menu or call to action repeats identically across pages of one publisher; the corpus designates it, no list:

- `html_template_keys`: each page yields keys "tag path + normalized text" for its leaf blocks (never a heading, code, table or
  IOC-bearing text).
- A key present in **≥ 40 %** of a source's pages (and ≥ **5 pages**) is template. A **full sentence** (≥ 6 words) repeated
  verbatim in **≥ 15 %** of articles is too (promotional insert of the period); shorter text may be a section title ("Indicators
  of compromise") and keeps the 40 % threshold.
- Persisted in SQLite table `site_boilerplate`, re-read at every `cti-classifier` run; `learn_site_boilerplate` relearns it over
  the corpus. Below 5 pages the template is empty and only structural detection acts. A source without `site_name` is keyed by
  the URL's domain (`site_key`).

### 3.3 Blocks, chunks, sections

- `split_blocks`: document blocks in order (`heading`, `code`, `table`, `text`) with their heading path. This is what lets
  extraction **number sentences** without re-implementing Markdown parsing.
- `chunk_markdown(max_chars)`: **non-overlapping** segments (so no duplicated IOC), never cutting a code block, table or
  paragraph; each heading stays with its first block; `oversized` flags a single block larger than the budget.
- Intrusion phases are inferred from section titles by whole word (`KNOWN_PHASES`: initial access … detection, YARA, Sigma).

### 3.4 Classification (`cti_classifier.py`)

The classifier **never sends the whole article**. `build_classifier_context` builds a compact, budgeted view:

```text
TITLE / STRUCTURE (sections, chars, code blocks, tables) / OUTLINE (full heading plan)
TEXT: introduction + prose sample per section + conclusion;  code and tables are only flagged: [omitted: code×2, table×1]
```

With too many sections, an evenly spread subset is sampled rather than truncating the end. Ollama (`qwen3.8:27b`, ≤ 160 output
tokens) answers `{"evidence": "<=20 words", "category": "...", "confidence": "high|medium|low"}`.

| Category | Meaning |
| :--- | :--- |
| `operational` | one concrete intrusion/campaign told in order (DFIR, timeline) |
| `tactical` | how a technique, tool, malware or vulnerability works or is detected |
| `strategic` | trends, geopolitics, sector/annual reports, little low-level detail |
| `out_of_scope` | not CTI: marketing, webinars, jobs, generic advice, empty or error pages |

Confidence becomes a score (high 0.9, medium 0.7, low 0.5; other classes 0). Results go to **`article_classifications`**
(`primary_category`, `score_*`, `rationale`, **`clean_markdown`**, `sections_meta`, `is_processable`, `reject_reason`,
`human_category`). **SQLite `clean_markdown` is the source of the cleaned text**; `data/cleaned/<site>/<hash>.md` is a readable
copy. Only `tactical`, `operational`, `strategic` are eligible for extraction.

`cti-audit` (Textual TUI) corrects categories by hand. `evaluate_cleaning.py` measures, without LLM, IOC fidelity (every IOC of
the visible page text must be in the cleaned text), residual noise and sources without template: **run it before ingesting a new
source**.

## 4. Extraction architecture

**Goal:** from the cleaned text, build a reliable **STIX 2.1 bundle**: entities, MITRE ATT&CK techniques, typed relations, IOCs
and detection rules, each relation **proven by sentence numbers** whose text the code re-reads.

### 4.1 Design ideas

1. **The model writes little, the code verifies everything.** Cost is dominated by *generated* tokens; reading the prompt is
   almost free when it starts like the previous one (prefix cache). All calls therefore start with the **same article text**
   and the model writes short lines only.
2. **Constrained output.** `llm.generate` enforces a JSON schema; each answer is lines like `a|b|c`.
3. **Proof = sentence number.** `segment.py` splits the article into numbered units. A relation cites `12,13` instead of copying
   a sentence: proof text is exact by construction. Code blocks and tables stay whole units but only an excerpt (8 code lines,
   14 table rows, 700 chars per sentence) is shown to the model; the full text remains available as proof.
4. **An ATT&CK technique always exists.** It is never written from memory: code proposes candidates, the model picks by letter.
5. **The LLM decides meaning**, never a deterministic rule on names; code proposes, bounds and informs.
6. **IOCs are read by rules**; the model only picks role and attachment.

### 4.2 Pipeline (`pipeline.py`, `extract_article`)

```text
clean_markdown
  │ segment.py: numbered sentences (Unit)
  ▼
1. PERCEPTION, in parallel (agents.py)                         common prefix: the whole article
   ├─ ThreatModelerAgent     threat actors, intrusion sets, campaigns, malware, tools
   ├─ TargetSpecialistAgent  victims, sectors, countries, targeted software, CVEs
   └─ TTPHunterAgent         behaviors: "sentences | tool | action and goal | tactic | presumed T####"
  ▼
   declare_entities: canonical registry in DraftGraph; CVEs re-read by rule from the text
  ▼
2. TECHNIQUES: find_candidates (ATT&CK FTS5) ─▶ batched choice call (letters) ─▶ accept_choices
   │ carrier of each technique: CarrierDisambiguationAgent (malware/tool > campaign > group)
  ▼
3. RELATIONS: RelationWeaverAgent ("source #|relation|target #|sentences")
   │ one correction call for refused lines; one call to connect "islands" (isolated components)
  ▼
4. VERIFICATION: the model judges each relation against its cited sentences (y/n);
   │ unsupported ones are dropped, with entities left without any relation
  ▼
5. OBSERVABLES: IOCs (rules + model role/attachment), YARA / Sigma rules (syntactic parsing)
  ▼
DraftGraph ─▶ semantic bundle article_<id>.json + observables bundle article_<id>.iocs.json ─▶ Neo4j
```

Steps are separate constrained calls. A failed step marks the article `llm_failures > 0` in Neo4j; it is **retried at the next
run**.

### 4.3 Step 1: entities and behaviors

| Agent (`CTI_MULTI_AGENT=on`, default) | Extracts |
| :--- | :--- |
| `ThreatModelerAgent` | `intrusion-set`, `threat-actor`, `campaign`, `malware`, `tool` |
| `TargetSpecialistAgent` | `identity` (victims, sectors), `location` (targeted countries), `software` (targeted product), `vulnerability` |
| `TTPHunterAgent` | one attacker behavior per line, described in English, with sentence numbers and a presumed ATT&CK id; `CTI_MULTI_TEMP` unions generations at T=0.2 and T=0.7 for recall |

Declared entities go through `DraftGraph.declare`: normalized name (`"<malware> (<file>)"` becomes name + alias), STIX type
checked by `stix2`, duplicates merged. Locations resolve to **ISO 3166-1 codes or STIX regions** (`places.py`); unresolved
ones are refused.

### 4.4 Step 2: ATT&CK techniques chosen, never invented

1. **Search** (`find_candidates`, `stix/attack.py`): per behavior, SQLite **FTS5** over the ATT&CK v20.0 index, two BM25 searches
   fused by RRF: one on technique name/description, one on their **17,636 procedure examples** ("APT29 used systeminfo to…"),
   the best lexical bridge between an article and ATT&CK. Procedures citing **the article itself** (`report_key`) are excluded,
   otherwise search would find a paraphrase of the article. `CTI_CANDIDATES` (6) sets the count, plus the presumed id and its
   parent technique.
2. **Choice**: one constrained call per batch (`CHOICE_BATCH`) shows each behavior's candidates with definitions; the model
   answers by letters. A retained technique therefore always exists, with its real id and name.
3. **Carrier**: `CarrierDisambiguationAgent` names the executing entity under a strict convention: a named malware/tool first,
   then a campaign, a group only if no executing entity is mentioned. Code creates the `uses` relation whose description is the
   English behavior (the procedure).

### 4.5 Steps 3–4: relations and verification

`RelationWeaverAgent` gets the article plus the **numbered registry** of retained entities/techniques and answers
`source #|relation|target #|sentence numbers`. Each line goes through `DraftGraph.relate`: the relation type must exist in the
`RELATIONS` table (`stix/objects.py`) for that pair of STIX types; `stix2` builds it strictly; cited sentences must exist. Refused
lines go back to the model **once** with the reason; a last call connects **islands** (the model links, the code only finds them).
Then the model judges each accepted relation against its cited sentences (batches of 40); unsupported ones are removed with
entities left without relation (unless `CTI_KEEP_ORPHANS=on`). Measured: the verifier removes ~30 relations per run, almost all
absent from the gold.

### 4.6 Step 5: observables (detection layer)

Separate from the semantic layer and from its evaluation.

- **IOCs** (`observables/iocs.py`): hashes, IPs, domains (real IANA TLDs, not file extensions), URLs, e-mails, read **by rules**
  in place. Discarded: the article publisher's own hosts, popular domains (Tranco), non-malicious URLs. The model only chooses
  **role** and **attachment entity**; an IOC judged non-malicious is dropped. Each IOC gets its text unit's observation date when
  unique and plausible.
- **Rules** (`observables/rules.py`): **YARA** (`yara-python`) and **Sigma** (YAML) copied as written by syntactic parsing; the
  model only picks the detected entity. A rule's text is never counted as an IOC list.
- Reference lists: `uv run python -m backend.extracting.observables.update_reference`.

### 4.7 LLM client (`llm.py`) and outputs

Constrained JSON schema (`generate`), **deterministic** decoding (temperature 0, `top_k` 1, fixed seed), reasoning off
(`CTI_THINKING=off`); `CTI_LLM_SLOTS` in-flight limit (`map_parallel` waits for a slot); `CTI_LLM_TIMEOUT` (180 s) closes the
connection so the server abandons generation; `--llm-log` writes every exchange to `article_<id>.llm.jsonl`; tokens counted by
the server.

| Output | Content |
| :--- | :--- |
| `backend/data/bundles/article_<id>.json` | **semantic layer**: report, entities, techniques, relations (what the gold describes, what `cti-eval` scores) |
| `backend/data/bundles/article_<id>.iocs.json` | **observables layer**: observables, indicators, observations, derived infrastructure, rules |
| Neo4j | both bundles; `(:Stix:<Type>)` nodes, typed edges, per-article provenance |

Bundles are **always written**, even with `--dry-run`; re-extraction overwrites them (annotate a copy).

Experimental variants: `CTI_SECTION_PASS=on` (behaviors also found per ~1,500-token block; helps long articles, +57 % time),
`CTI_CARRIER=on`, `CTI_OPERATIONS=on` (campaigns decided by a separate call), `CTI_SECOND_LOOK`, `CTI_VICTIMS`, `CTI_MENTIONS`.
Any system-prompt edit can make a campaign vanish at the margin: measure it as a method change, on ≥ 2 runs (vLLM under
concurrent requests is not strictly deterministic).

## 5. Storage, dashboard, evaluation

- **Neo4j** is the **only** persistence of the graph. `stix_store.py` writes `(:Stix:<Type>)` nodes, typed edges and
  **per-article provenance**: every node and edge carries the list of articles supporting it, so removing an article removes only
  its contribution. SQLite is **read-only** for extraction and dashboard. A deleted article is marked `(:DeletedArticle)` and
  skipped by `cti-extract` unless `--article-id` or `--force`.
- **Dashboard** (`scripts/dashboard.sh`, port 8095): *CTI Reports* (one incident's graph, IOCs, rules, timeline), *Threat Actors*
  (hierarchical org chart: country/identity, actor, divisions, then Arsenal / Techniques / Infrastructure / Targets; an empty
  heading stays empty, never inferred), *Global graph* (all articles, sigma.js WebGL, filter by minimum source articles) with a
  panel that **queries the graph by LLM** (`dashboard/ask.py`: read-only bounded tools, no model-written Cypher, short refs
  `[[E3]]`, unknown citations removed; `CTI_ASK_SLOTS` = 1).
- **Evaluation**: gold in `Annotations/manifest.json`. The Python backend has no unit tests; `cti-eval` is the regression test.

  ```bash
  uv run cti-eval --run --workers 4 --bundles backend/evaluation/eval/<name>    # extract + score
  uv run cti-eval --bundles backend/evaluation/eval/<name>                      # re-score, no model call
  uv run cti-eval --compare v5_base_1,v5_base_2 <a>,<b>                         # delta + 95 % bootstrap CI
  ```

  Report: recall, precision, partial credit, hallucinations, grounding, strict and relaxed scores, per-stage technique losses,
  relations removed by the verifier. Reference (`v5_base_1/2`, semantic layer): entities R 63.1 / 63.7 %, P 68.8 / 68.7 %;
  relations R 30.7 / 30.3 %, P 38.7 / 35.5 %. **No gold leakage**: no proper name or identifier from annotated articles in
  prompts or code (use templates such as `<malware>`, `T####.###`); `Annotations/holdout/` is never used for tuning.

## 8. Troubleshooting

| Symptom | Cause / fix |
| :--- | :--- |
| `uv sync` fails on `cti_core` | no/old `cargo`: install Rust, rerun |
| vLLM engine fails at init | wrong/busy GPU: set `CUDA_VISIBLE_DEVICES`; or lower `--max-model-len` / `--max-num-seqs` |
| HTTP errors on extraction calls | server started without `--enable-auto-tool-choice --tool-call-parser qwen3_coder` |
| Article failed on context length | article exceeds `--max-model-len` |
| Timeouts, slow calls | `CTI_LLM_SLOTS` or `--workers` > `--max-num-seqs`: server queue grows, preemptions in `/metrics` |
| Model answers but ignores the text | badly loaded weights: redo the 17×23 check |
| Ollama reloads the model each request | mismatched `num_ctx`: align `OLLAMA_CONTEXT_LENGTH` and `OLLAMA_NUM_CTX` |
| `connection refused` on 8010 / 11434 | SSH tunnel closed |
| Dashboard empty | no data in Neo4j; ports 8080/8090 belong to a local OpenCTI, use 8095 |
| Scores differ between runs | expected: compare ≥ 2 runs with `cti-eval --compare` |

## 9. Invariants

1. **Per-article isolation**: a report shows only its own subgraph; the global graph and Actors view are explicit aggregate views.
2. **Grounding**: relations cite sentence numbers; proof text is re-read by code.
3. **No invention**: unknown ATT&CK ids, unresolved locations are refused; empty profile headings stay empty.
4. **Anti-noise**: researchers, security vendors and victim companies are never threat actors; native binaries
   (`powershell.exe`, `certutil.exe`) are dual-use tools, never C2 infrastructure.
5. **Universal preprocessing**: no publisher/actor/tool list in Rust; IOCs stay in place.
6. **IOCs by rules**; the model picks only role and attachment.
7. **Remote servers**: no local `ollama`/`vllm`/`systemctl`; never more requests than slots.
8. **No gold leakage** into prompts or code.
